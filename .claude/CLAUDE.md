# SGXP Project Context

## Project Overview
The SGXP is an open-source sprite website where users can upload sprite sheets, sprite comics, and showcase their WIP art. This is a complete rewrite of the original PHP-based site using modern web technologies.

## Tech Stack
- **Framework**: Astro 5 (server-side rendering and routing)
- **UI Components**: Svelte 5 (all components are Svelte, no React)
- **Component Library**: shadcn-svelte (Svelte-specific variation of shadcn)
- **Styling**: Custom stylesheets with Tailwind CSS 4
- **CMS**: Payload CMS (external, handles content management and PostgreSQL database)
- **Database**: PostgreSQL (managed by Payload CMS, external to this project)
- **Storage**: AWS S3 (sprite sheet uploads and media storage)
- **Icons**: Lucide Svelte

## Key Conventions
- Use 2-space indentation
- All components must be Svelte 5 components (no React)
- Use shadcn-svelte components, not vanilla shadcn
- Database interactions happen through Payload CMS API, not direct queries
- Custom stylesheets take precedence; Tailwind is supplementary

## Buttons (the button standard - applies to every new or changed button)
- **Every button is `<Button>` from `$lib/components` with a standard `variant`.** No new hand-styled `<button>`s and no new custom button CSS. Styles: `src/styles/buttons.css`; every variant and state on the dev-only reference page `/dev/buttons` - check it before building anything button-like.
- Variants: `primary` (the main action), `secondary` (supporting actions; also pagination, with the current page as `aria-current="page"`), `danger` (deletes/removes), `toggle` (on/off or selected state via `aria-pressed`; side-by-side toggles go in `ButtonGroup`), `tool` (boxed icon buttons), `subtle` (unboxed icon inside content), `quiet` (low-emphasis uppercase text action - provisional). Sizes: `default`, `mini` (24px), `icon`, `icon-mini`.
- **Primary buttons always get an `icon`** that describes the action (lucide for now; sprite icons someday). Icon-only buttons need an `aria-label`. Two-state icon buttons (e.g. bookmark) set `aria-pressed` - their icon fills in automatically.
- Never set a button's height, colors, radius or shadow by hand: sizes use `--control-height` (42px on desktop and phones), which search inputs share so toolbars line up.
- Anything that waits on the server uses `loading` (disables the button and shows the site `Spinner`) - don't hand-roll "Saving..." spinners.
- If no variant fits, stop and ask the user rather than inventing a one-off look. Exceptions: navbar items keep their own pixel-font look.
- **Every solution references the standard, so a change in `buttons.css` tracks across its whole category.** Page CSS may only set *layout* on a button (position, margins, width/flex, gaps) - never colour, border, shadow, font, icon colour or size. Anything visual a page needs becomes a documented option in `buttons.css` and on `/dev/buttons`: counts (`sgxp-btn-count`), badges (`sgxp-btn-badge`, `--corner`), plain arrow icons (`data-icon="plain"`), icon fill opt-in/out (`data-icon-fill="true"/"false"`), and non-clickable boxes that match a button (`sgxpButtonClass({ variant, size, static: true })`). Buttons that can't be `<Button>` (portalled/animated elements, popover triggers, pagination links) use `sgxpButtonClass(...)`.
- Pages are being migrated one commit at a time (started 2026-09-26); buttons with `themed` or stock shadcn variants (`default`/`outline`/`ghost`) are pre-standard and get converted when their page is migrated.

## Discord Bot (`/discord-bot`)
A standalone Node service, separate from the Astro app, deployed as its own Coolify app from the `discord-bot/` subdirectory (own `Dockerfile`, own `package.json`, npm not pnpm). Built 2026-08-26 for personal push notifications (phone alerts via Discord DM) plus public-facing posts to the SGXP Discord server (daily leaderboard; birthdays are handled manually outside the website/bot).

- **Uses `discord.js` v14, gateway-based** — connects outbound to Discord, so it needs no public inbound URL/subdomain for Discord's sake.
- **Data access**: calls the same Payload CMS REST API the website uses (`PAYLOAD_URL`), via `src/payload.js`. No direct DB access, no local Payload config.
- **Real-time notifications**: the site forwards events to the bot's internal `POST /events` endpoint (bearer-secret protected, see `src/server.js`) via `src/lib/discordBot.ts`'s `notifyDiscordBot()`, called from the site's Payload webhook handlers (e.g. `src/pages/api/webhooks/sprite-updated.ts` on `sprite.created`). Prefer internal Docker networking between the two Coolify apps over exposing this endpoint publicly — nothing about the bot needs to be internet-facing.
- `sprite.created` (owner DM only, unchanged) fires on every new upload regardless of approval status. A separate `sprite.approved` event (added 2026-09-17) fires the FIRST time a sprite is approved, and publicly posts an embed (title/author/image/link) to `DISCORD_FINISHED_ART_CHANNEL_ID`. Leave that env var unset to skip the public post. Note: the CMS's webhook body previously never included `status` or any image URL at all — approving a sprite silently notified nobody before this fix, since a pure status change produces an empty `buildSpriteDiff` diff and the old code bailed out on empty diffs.
  - **A naive `previousDoc.status !== 'approved' && doc.status === 'approved'` transition check is NOT enough** — editing an already-approved sprite resets its status back to `'pending'` (`sgxp`'s `src/pages/api/sprites/[id].ts:577`, `hasNonColorChanges` check), so re-approving an edited sprite would look identical to a first-time approval and would repost publicly, which is explicitly unwanted. Fixed with a persistent `Sprites.announcedAt` (date) field: set once, in the same `afterChange` hook, via a deferred `req.payload.update` right after the webhook fires (mirrors the existing prestige-role-update hook's `setImmediate` pattern in the same file, to escape the parent request's transaction). `becameApproved` is gated on `!doc?.announcedAt` in addition to the status transition, so a later edit → re-approve cycle never re-fires the public post, only the very first approval does.
- **Scheduled jobs** (`src/jobs.js`, `node-cron`): daily sprite leaderboard post to `DISCORD_ANNOUNCE_CHANNEL_ID` (top sprites by likes), and a second daily archive triage leaderboard post 15 minutes later to `DISCORD_ARCHIVE_CHANNEL_ID` (falls back to `DISCORD_ANNOUNCE_CHANNEL_ID` if unset) — both built from `src/archiveLeaderboardEmbed.js`, shared with the `/archiveleaderboard` command below.
- **Slash commands** (`src/commands/`): `/stats` (site totals), `/leaderboard` (top sprites), `/archiveleaderboard` (archive triage: total/sorted/kept/excluded stats + top 5 preparers/reviewers). Register/update them via `npm run deploy-commands` after changing any command definition — Discord doesn't pick up command changes automatically. Set `DISCORD_DEV_GUILD_ID` for instant per-guild registration during development; omit in production for global registration (propagates slower).
- **`archive-entries` requires a logged-in user to read at all** (unlike `sprites`/`users`, which have public read) — the bot has no login session, so `getArchiveLeaderboard()`/`getArchiveStats()` in `src/payload.js` authenticate via `PAYLOAD_API_KEY` (the same admin API key used for `grantArchivistAccess`) rather than the plain unauthenticated `payloadFetch()` the sprite/stats commands use.
- **One-off testing**: `node src/test-message.js <channelId> "message"` logs in, sends a single message, and exits — useful for verifying the bot can post without running the full process.
- Env vars are documented in `discord-bot/.env.example`. The **Public Key** from the Discord Developer Portal is NOT used (that's only for HTTP-interaction bots; this one uses the gateway) — don't add it expecting it to do anything.
- **Actionable DM buttons** (`src/archivistActions.js`): the `archivist.requested` event attaches a "Grant Archivist Access" button to the owner's DM (built in `server.js`, handled via `Events.InteractionCreate` in `index.js`). Clicking it calls `payload.js`'s `grantArchivistAccess()`, which PATCHes Payload authenticated as an admin user via API key (`PAYLOAD_API_KEY` env var, requires `useAPIKey: true` on the CMS's `Users` collection and generating a key from that admin's own profile page in the Payload admin panel — Payload has no way to generate this key programmatically, it's a manual one-time admin-panel step). This is the pattern to extend for any future "act on this from Discord" feature — build the button in the event handler, gate the click to `DISCORD_OWNER_USER_ID`, and always `deferUpdate()`/`editReply()` rather than a bare `reply()`/`update()` since the Payload round-trip can exceed Discord's 3-second interaction window.

## Known Bugs & Quirks (learned 2026-08-26, archive triage feature work)

- **`src/utils/auth.js` returns the wrong shape.** `verifyToken`/`getUserFromRequest` return Payload's raw `/api/users/me` response (`{ user, token, exp }`) unmodified — NOT the unwrapped user. Any code that does `user.role` on the result of `getUserFromRequest` will always get `undefined`, silently breaking role checks (this caused a real bug where admins were redirected out of a role-gated page). **Use `resolveUser(cookies)` from `src/lib/userCache.ts` instead** — it correctly does `data.user || data` and also caches to a cookie. Prefer it over `utils/auth.js` for any new page needing the current user.

- **TanStack table (`src/components/ui/data-table/create-svelte-table.svelte.ts`) reactivity is fragile for client-only, empty-then-fetch components.** The wrapper mutates a long-lived `table` instance via getters + a nested `$effect`/`setOptions` chain. The one existing usage (`UserUploadsViewer.svelte`) never actually exercises "start empty, fetch async, re-render with new data" — it pre-populates from SSR props (`initialSprites`) and explicitly skips the first client fetch. A new `client:only="svelte"` table component that starts with empty `$state` and populates it via `fetch()` may not reliably re-render.
  - **Fix that worked**: don't hold `table` as a plain `const`. Build it as `let table = $derived.by(() => createSvelteTable({ data: entries, state: { pagination, sorting }, ... }))` using plain values (not getters) — this creates a fresh table instance whenever the actual `$state` inputs change, which is guaranteed-correct Svelte 5 reactivity instead of relying on the wrapper's internal option-merging timing.
  - Also initialize any `isLoading` flag to `true` (not `false`) when a component always fetches on mount — otherwise there's a flash where `isLoading=false && data=[]` renders an "empty" state before the effect even runs once.

- **`.dockerignore`'s corrupted first line (`2213n.3ode_modules`) was fixed 2026-08-27** — it's `node_modules` now. (It had been sitting as an uncommitted local-only change the whole time, never actually in a commit — worth double-checking `git diff .dockerignore` if this ever looks wrong again.)

- **MSYS/Git-Bash `ps`/`kill` PIDs don't match real Windows PIDs.** To reliably kill/inspect a specific dev server process on Windows from this shell, use `netstat -ano | grep :<port>` to get the real Windows PID, then `taskkill //PID <pid> //F` — plain bash `kill <pid>` from `ps aux` output often targets the wrong (MSYS-subsystem) process tree entirely.

- **`createRawSnippet` + a hand-built HTML template string is unsafe for real user/scraped content.** Used for table cells showing comic titles (`ArchiveTriageTable.svelte`), it crashed with `Uncaught TypeError: 'get nextSibling' called on an object that does not implement interface Node` once real data (34k+ titles) landed — any title containing `&`, `<`, or `>` (521 of them did, e.g. "Yoshi & Kirby") corrupts the HTML structure Svelte's compiler expects. Fix: use a tiny real Svelte component with normal `{value}` text interpolation (auto-escaped) instead of `createRawSnippet`/raw template literals — `createRawSnippet` is for pre-sanitized trusted HTML only, never for arbitrary text.

- **`JSON.stringify({field: undefined})` produces `{}` — the key vanishes entirely.** A PATCH body built as `JSON.stringify({ [field]: value })` silently does nothing if you intend "clear this field" via `value = undefined` — the key never reaches the server, so the old value stays. To actually clear/unset a field over the API, send `null` explicitly, not `undefined`.

- **The installed `lucide-svelte` (0.544.0) renamed some icons from their older/more-commonly-known names** — `Loader2` doesn't exist anymore, it's `LoaderCircle` now (confirmed by grepping `node_modules/lucide-svelte/dist/icons/index.js`; `Check` is unaffected). A `Loader2` import fails silently at the Svelte-compile level (compiler doesn't check named imports exist) and only breaks at runtime/bundle time. Before using any lucide icon by a name you're not 100% sure of, grep the installed `dist/icons/index.js` first.

- **When talking to Payload's REST API directly from a Svelte component's `catch` block, always check `data.errors?.[0]?.message` before `data.message`** — Payload wraps every HTTP error as `{ errors: [{ message }] }`, there is no top-level `message` (see `sgxp-cms/CLAUDE.md` for the full explanation). Checking `data.message` alone always silently falls back to whatever generic string you wrote, hiding the real backend validation reason from the user.

- **Prefer an explicit user-triggered action over an automatic side-effect of editing a field**, when the action represents a meaningful workflow commitment (e.g. "submit this for review"). Originally, editing the sprite-comic/game-related checkboxes silently auto-transitioned an entry to "prepared" — this surprised the user ("the comic shouldn't go into review automatically") and got reverted in favor of a dedicated "Ready for review" checkbox/button that's the *only* thing allowed to trigger that transition. If a state transition has real consequences (locking fields, crediting a specific user, notifying someone), make the user click something that says so, rather than inferring intent from an unrelated edit.

- **TanStack column headers aren't clickable/sortable by default just because `getSortedRowModel`/`onSortingChange` are wired up** — nothing in this codebase's shared `DataTable.svelte`/`Table.*` primitives renders a sort affordance on headers (checked: `UserUploadsViewer.svelte` has the same latent gap). The correct shadcn-svelte pattern (confirmed via their docs) is per-column: `header: ({column}) => renderComponent(SortButton, { onclick: column.getToggleSortingHandler() })`, a ghost-variant `Button` + `ArrowUpDown`/`ArrowUp`/`ArrowDown` lucide icon reflecting `column.getIsSorted()`. This is a per-column opt-in, not something to bake into the shared table primitives.

- **Postgres enum columns sort by their declaration order, not alphabetically** (`pg_enum.enumsortorder`). Verified directly against the DB. Useful trick: if a select field's `options` array is declared in the priority order you want (e.g. `unsorted, identified, uploaded`), a plain ascending `sort=fieldName` on that column already returns rows in that priority — no need for a custom sort key.

- **shadcn's `Select` trigger (`Select.svelte`'s `.theme-select-trigger`) is hardcoded to `height: 42px`, but the base `Input` component defaults to shadcn's own `h-9` (36px).** They visually mismatch when placed side-by-side in a toolbar unless one is explicitly overridden to match the other.

- **`Combobox.svelte` (`$lib/components/ui/base`) is the better choice over `Select` for long option lists** (e.g. the 25-item category list) — it has its own built-in search filter and a custom scrollable list, and doesn't have bits-ui `Select`'s auto-rendered click-to-scroll chevron buttons (`data-slot="select-scroll-up-button"`/`"-down-button"`) that appear once a plain `Select`'s content overflows.

## Known Bugs & Quirks (learned 2026-08-27/28, archive triage live-update work)

- **This project has two parallel "shadcn" layers — don't confuse them.** `src/components/ui/<name>/` holds genuine CLI-generated shadcn-svelte primitives (e.g. `button/button.svelte` with its `tv()` variants, using `@/lib/utils` and `@/components/ui/...` import aliases). `src/lib/components/ui/base/<Name>.svelte` are this project's own *themed wrapper* components around those primitives (adding the `themed` prop, `.theme-*` CSS, and app-specific convenience props), re-exported from `$lib/components`. When adding a new shadcn-svelte component (e.g. we added `toggle`/`toggle-group` this way), fetch the real source from `https://shadcn-svelte.com/registry/<name>.json` (its `$UTILS$`/`$UI$` placeholders map to `@/lib/utils`/`@/components/ui` here), drop it under `src/components/ui/<name>/` unmodified, then write a themed wrapper in `src/lib/components/ui/base/` if app code needs one — don't hand-roll a look-alike component from scratch.

- **`EditableSelectCell`/`EditableComboboxCell` silently swap the real control for plain readonly text whenever `disabled` is true** (their own `{#if disabled}<span class="readonly-value">...` branch) — this is the right look for genuinely locked rows (e.g. `rowLocked`/`flagsLocked`), but wrong for "temporarily not applicable, should look faded but still look like the control" (e.g. Category/Rating before an entry is marked a sprite comic). Both cells now take an additional `faded` prop that bypasses the readonly-text branch and renders the real `Select`/`Combobox` with `disabled` passed through instead — added because the base `Select`/`Combobox` wrappers didn't support a `disabled` prop at all before this (now do, styled via Tailwind's `disabled:opacity-50` on `Select`'s trigger and a plain `:disabled` CSS rule added to `Combobox`'s trigger). Reach for `faded` before duplicating this disabled-but-visible pattern elsewhere.

- **This app's local dev `.env` points `PAYLOAD_URL` at production CMS (`https://cms.sgxp.me`), not a local Payload instance.** Easy to forget mid-session and accidentally test/mutate real production data while believing you're on `localhost`, or to test a feature against `localhost` while the thing you're actually trying to verify (e.g. a Payload webhook that only knows about the deployed `SITE_URL`) can only ever reach the real deployed site. Double-check which URL a running dev server is actually pointed at, and which page/tab you're looking at, before concluding a live-update feature "isn't working."

- **Coolify's per-app Gzip Compression setting can silently swallow a Server-Sent Events stream with zero errors anywhere in the stack.** Building live-update-over-SSE for the archive triage table (`src/pages/api/archive-entries/stream.ts`, fed by a Payload `afterChange` hook webhook), every layer of logging showed success — SSE client connected, webhook received, broadcast enqueued to N clients — but the browser's `EventSource` never received the `entry-updated` message (confirmed via `onopen` firing but no message ever logging, i.e. the connection opens fine but body bytes never arrive). Cause: compression buffers the response before it can flush, which defeats a long-lived stream that's supposed to deliver small chunks in real time. Fix: disable Gzip Compression in Coolify's app settings for any app that serves an SSE/streaming endpoint (done for both the `sgxp` and `sgxp-cms` containers). `X-Accel-Buffering: no` on the response is cheap insurance but did not by itself fix this — the Coolify-level toggle was what mattered. If a future streaming/SSE endpoint "connects but never receives messages," check this setting before assuming the app code is wrong.

- **When Payload's REST webhook docs/comments describe a hook that "should" call the site, verify the actual code exists before assuming it's wired up.** `sprite-updated.ts` had a doc comment saying "Configure this webhook in Payload CMS" but grepping the entire `sgxp-cms` repo found no matching `fetch`/webhook call anywhere — it's unclear whether that one is actually configured (maybe via the admin UI, maybe never finished). The archive-entries live-update hook was written from scratch in `ArchiveEntries.ts`'s `afterChange` array as a `setImmediate`-wrapped fire-and-forget `fetch()` (mirroring the existing prepared/reviewed-count-increment hook's pattern) rather than assuming the sprite one was a working template to copy.

- **This repo has no real Payload migrations — schema changes only reach production via `next dev`'s auto-push, run locally against the prod `DATABASE_URI`.** Confirmed in `@payloadcms/db-postgres`'s `connect.js`: `pushDevSchema` only runs when `NODE_ENV !== 'production'`, and the production container (`next start`, `NODE_ENV=production` in the Dockerfile) never does this — there's also no `migrations/` directory and no `prodMigrations` config, so there's no other path for new columns to reach prod. After adding/changing any field on a Payload collection, you must run `npm run dev` in `sgxp-cms` locally (it points at the real prod DB) and hit any Payload route (e.g. `curl localhost:PORT/api/users/me`) to force initialization and trigger the push — Payload only pushes lazily on first request, not at server boot. Verify it actually landed with a raw query (`information_schema.columns`) before assuming it worked, then kill the local server. `admin.readOnly` on a field is a UI-only restriction (doesn't affect API access) — don't reach for it to "protect" a field from the API; use `access.update` for that.

- **Per-user targeted SSE (as opposed to broadcast-to-everyone) needs the connection registry keyed by user ID, not just a flat `Set` of controllers.** Added to `archiveEventHub.ts` for the "archivist access granted" live push: `addArchiveEventClient(controller, userId)` returns a `{controller, userId}` record, and `notifyUserAccessGranted(userId)` filters connected clients down to that one user before sending — versus `broadcastArchiveEntryChange` which still sends to everyone. Same hub, same single `/api/archive-entries/stream` connection carries both event types (`entry-updated` broadcast, `access-granted` targeted) — no need for a second EventSource per concern.

- **`resolveUser`'s 5-minute user-info cache can show stale permission state after an out-of-band grant.** The Discord bot's "Grant Archivist Access" button PATCHes Payload directly, which never touches the site's `sgxp-user` cookie cache — so a page reload within that 5-minute window kept showing "Request Pending" even though access was actually granted. Fixed two ways: `resolveUser(cookies, { forceFresh: true })` skips the cache entirely for the archive triage page (a low-traffic, permission-sensitive page where correctness matters more than saving one Payload round-trip), and the live SSE `access-granted` push (previous note) updates the open page instantly without even needing a reload. Reach for `forceFresh` on any other page where an out-of-band permission change needs to be reflected immediately.

- **2026-08-28: `archive-entries`' `status` and `reviewStage` fields were merged into one unified 5-value `status` pipeline** (`Unsorted → Ready for Review → Ready for Rating → Ready to Upload → Uploaded`), and the dormant unused `readyToUpload` (yes/no) field was dropped entirely. Archivists can drive `unsorted → ready-for-review → ready-for-rating` themselves (validated in `ArchiveEntries.ts`'s `beforeChange`); the last two steps are admin-only, gated by `archivistAccess`'s Where clause (`status not_in [ready-for-rating, ready-to-upload, uploaded]`) rather than per-field access checks — once a doc is in one of those three states, the *entire document* is inaccessible to non-admin writes, which is why the old per-field `access.update` checks on `isSpriteComic`/`isGameRelated` (previously keyed on `reviewStage !== 'reviewed'`) could just be deleted instead of updated. The frontend mirrors this with one `locked(entry)` helper (replacing the old separate `flagsLocked`/`rowLocked` pair) checking `STATUS_ORDER.indexOf(status) >= STATUS_ORDER.indexOf('ready-for-rating')`.
  - **Migration approach for a live enum + live data, no real migrations system**: (1) `ALTER TYPE ... ADD VALUE IF NOT EXISTS` for each new status value first (additive, safe, can't be undone but also can't break anything) — do this *before* touching Payload code, since you need the DB to accept the new values before any UPDATE can write them. (2) Run the data-remapping `UPDATE` statements directly via raw SQL while the *old* columns (`review_stage`) still exist, since you need their values to decide the mapping. (3) Only after that, `ALTER TABLE ... DROP COLUMN` the obsolete columns directly via raw SQL yourself — do NOT rely on the `next dev` auto-push to detect and drop them, since drizzle-kit's push prompts interactively for destructive changes and a scripted/headless push can't answer that prompt (this project's `sgxp-cms/CLAUDE.md` already documents a related "blocks the entire config from loading" failure mode for incompatible-type pushes). (4) Deliberately did *not* try to remove the now-unused `identified` value from the Postgres enum type itself — Postgres has no `DROP VALUE`, only a full type-recreation dance, and leaving an orphaned unused enum member is completely harmless as long as no code path writes it anymore.

## Known Bugs & Quirks (learned 2026-09-09, pulling latest repo state)

- **When asked to "pull the latest version of the repo," don't trust `git status`'s "up to date" line alone — it only reflects the last `fetch`, which can be stale.** Always `git fetch origin` first, then compare (`git log HEAD..origin/master --oneline` or check `git status` again post-fetch) before concluding there's nothing new. This surfaced when a prior "already up to date" check turned out to just be checking against stale remote-tracking refs — a fresh fetch showed the local branch was actually 4 commits behind.
- **An untracked file that collides with one newly added upstream (e.g. `pnpm-lock.yaml` regenerated locally via `pnpm install`, then added to the repo in a remote commit) will abort a fast-forward `git pull`** with "untracked working tree files would be overwritten by merge." Per this project's general safety rule (check `git status`/diff before anything that could discard work), don't delete the untracked file to force the pull — move it aside first (e.g. `mv pnpm-lock.yaml pnpm-lock.yaml.local-backup`), pull, then diff the backup against the new tracked version and only delete the backup once confirmed safe to discard.

## Known Bugs & Quirks (learned 2026-09-02/03, SmackJeeves archive completeness & content-flagging work)

- **A local `npm run dev` schema push (against the prod DB) only creates the DB columns — it does NOT make the already-deployed production Payload API recognize or return the new fields.** Added 5 new fields to `ArchiveEntries` (`sourceGenres`, `sourceTags`, `sourceIsMature`, `sourceContentFlag`, `sourceMetadataFetchedAt`) via a local dev server per the existing "no real migrations" quirk above — the columns landed in Postgres immediately, but a PATCH/GET against the live `cms.sgxp.me` API silently ignored/omitted them entirely (no error) until `sgxp-cms` was actually committed and pushed (it auto-deploys via Coolify, unlike `sgxp`). The running production Next.js process has the OLD compiled Payload config in memory regardless of what the DB schema now allows. **Always redeploy `sgxp-cms` after a schema-push session, before assuming the new fields are usable via the API** — verify with a real GET/PATCH round-trip against `cms.sgxp.me`, not just the raw SQL column check.

- **Every SmackJeeves comic on archive.org has a per-comic `metadata.json`/`metadata.js` file preserving the original site's own genre/tag/maturity data** — found at `<archive.org item>/<comicId>/comic/metadata.json` (also mirrored at `<comicId>/metadata.js`, wrapped as `let metadata = {...}`). Same files exist on the network drive at `smackjeeves-<id>/<id>/comic/metadata.json` under `smackjeevesfull`, `smackjeevesfinished`, `smackjeevesonline`, and the `1TB Transfer (WII GAMES)/smackjeeves` top-level folder (NOT in `bigfolder`, which only has sample page images). Key fields: `genres` (small fixed taxonomy — Action/Comedy/Drama/Fantasy/Horror/Mystery/Romance/Sci-Fi/Everyday/Campus/Other, plus `BL`/`GL` for boys'-love/girls'-love), `tags` (free-text, author-supplied), `isMature` (boolean), `description`/`shortDescription`.
  - **`isMature` is a broad "not for general audiences" flag, NOT sexual-content-specific** — verified by checking it against the 881 already-approved/uploaded comics: 33 of them (3.8%) are `isMature: true` with titles indicating violence/profanity/crude humor, zero of them tripping the sexual/LGBT+ keyword or `BL`/`GL` genre signal. Never auto-exclude on `isMature` alone.
  - **`tags` has terrible coverage (19.9% of comics have any tag at all) — `description` has excellent coverage (94.8%).** Any future recall-improvement work on content classification should mine `description` text, not just `tags`, but expect much higher false-positive noise from natural-language negation ("no porn allowed", "NOT yaoi") that structured tags don't have — this is why `sourceContentFlag` (see below) was deliberately built from `genres`/`tags` only, not `description`.
  - **13 comic IDs exist as folders on the network drive with no `comicId` in the DB at all**, and separately **15 comic IDs have a folder but no `metadata.json` inside it** (6 of those are also 404 on archive.org — genuinely gone). See `docs/smackjeeves-archive-status.md` for the full completeness audit (confirmed: the archive-entries DB is a complete 1:1 mirror of the entire 34,742-item `smackjeeves-web-comics` archive.org collection).

- **`ArchiveEntries.sourceGenres`/`sourceTags`/`sourceIsMature`/`sourceContentFlag`/`sourceMetadataFetchedAt`** (added 2026-09-03): backend-only classification fields, backfilled for all 34,736 reachable comics directly from local `metadata.json` files over SSH to the TrueNAS box (see below) — no archive.org calls needed once the network drive is reachable. Public read (matches the rest of the collection), admin-only write. **Not surfaced as triage-table columns on purpose** — meant for backend querying (`where[sourceContentFlag][equals]=true`), not the archivist-facing UI. `sourceContentFlag` is `true` when `sourceGenres` includes `BL`/`GL` OR `sourceTags` matches a curated keyword list covering sexual content of any orientation (deliberately broad — includes `heterosexual`/`asexual`/`bisexual`/etc., not just same-sex terms), LGBT+ identity, and underage/loli-shota concerns. As of 2026-09-03: 1,313 comics flagged, of which 1,264 (then-unsorted) plus 427 separately-identified blank/pageless comics (from `comicswithoutpages.txt` on the network drive) were bulk-marked `excluded` (preparedBy/reviewedBy both set to user 35/Xypter, with a distinguishing `notes` string per category) — dropping `unsorted` from 25,753 to 24,062.

- **TrueNAS box hosting the network drive is SSH-reachable at `root@192.168.117.7`** (key: `~/.ssh/truenas_brazil` on this machine) — Linux (TrueNAS SCALE), `python3`/`jq` available, no `node`. ## Known Bugs & Quirks (learned 2026-09-22, performance pass + navbar pixel-font work)

- **Production compression lives in `server.mjs`, not Coolify.** Coolify's Gzip toggle must stay OFF for `sgxp` (it buffers SSE - see the 2026-08-27/28 note). `server.mjs` wraps `dist/server/entry.mjs`'s exported `handler` (started with `ASTRO_NODE_AUTOSTART=disabled`) in the `compression` package, skipping `text/event-stream`, and gives `public/` assets a 1-day `Cache-Control` (the adapter's own static server only sets `max-age=0` for them, and only when nothing set a header first). It's the Dockerfile `CMD` and `npm start`. `/sprites` went 550KB -> 27KB on the wire.

- **Sprite list fetches are trimmed with Payload `select`/`populate`** via `src/lib/spriteListQuery.ts` (used by `sprites.astro` SSR and `SpriteBrowser`'s `fetchSprites`). The list data is handed straight to `SpriteViewer` as `initialSprite` without a refetch, so only drop fields nothing reads. **Media `prefix` must stay populated** - Payload's S3 adapter builds `url` from it; without it every image URL silently loses its `/media/` segment.

- **Astro's ClientRouter and the in-page sprite viewer.** `SpriteBrowser` opens sprites with a raw `history.pushState`; on Back, Astro's own `popstate` listener always runs *before* any component listener (even capture-phase on `window`) and treats it as a real navigation (spinner, full `/sprites` refetch, page swap). Cancelling `astro:before-preparation` makes Astro do a full `location.href` reload instead, so the fix neutralizes the navigation: a custom `event.loader` that hands back `document`, a no-op `astro:before-swap` `event.swap`, and a skipped view transition (with its promises' AbortErrors swallowed). Direct page loads never showed the bug only because their history entry has `null` state, which Astro ignores - always test navigations by *arriving via the navbar*.

- **Chrome on Windows blurs pixel fonts** whenever text sits on a composited layer that's animating/fading/scaled (LCD -> grayscale AA switch). No CSS switch fixes it (`-webkit-font-smoothing` is macOS-only). The desktop navbar now renders its `nav`-font labels as images: `src/components/PixelText.svelte` + atlas data `src/lib/pixelFonts/navFont.ts`, both generated by `scripts/generate-pixel-font-atlas.py` from the font file (pure pixel fonts only; it verifies). Letters are a CSS `mask-image` (so they take the theme's `--font-color`); the `#1D1D20` outline is a baked separate atlas. Atlases live on R2 at `img/fonts/nav-font-{fill,outline}-vN.png` (immutable). `PixelText` needs a `lineHeight` prop when its parent has an explicit `line-height` (dropdown items use `lineHeight={22}`). The dropdown carets `▾`/`▴` are generator-derived glyphs (the font's `>` rotated) and swap on the trigger's `data-state` instead of rotating.
  - **Upload new atlas PNGs to R2 BEFORE pointing `navFont.ts` at them.** Cloudflare answers a not-yet-uploaded URL with a 404 that browsers cache for 4 hours (`Cache-Control: max-age=14400`), which looks like "letters missing in one browser" long after the upload lands. Always bump `--version`; never overwrite an uploaded atlas.

- **`BN6FontTinyExt.ttf` (the `nav`/`title` font) had contradictory vertical metrics** (hhea 682/0 vs OS/2 typo 768/-256), and Chrome/Firefox read different tables, so text sat at different heights per browser. `BN6FontTinyExt-fixed.ttf` (same glyphs, all tables 768/256/0 + USE_TYPO_METRICS) is what `global.css` now loads; the original is kept unmodified alongside. Even with fixed metrics, Firefox computes `line-height: normal` for this font differently from Chrome - use explicit pixel line-heights with it.

- **Sprite-card glyph text (`.sprite-text`) uses a metrics-override copy of saira** (`sprite-text-metrics` in `sprite_icon.css`: ascent 110% / descent 50% / gap 0). The characters are background-image spans on the text baseline, and saira's real metrics put that baseline on a half pixel that Firefox (unlike Chrome) doesn't round - a 1px drop on every card in Firefox only. Previously masked by the cards' old `translateY(-.1px)`, which was removed (it forced a GPU layer on every card and nudged hovered text). Verify card changes by comparing glyph positions in *both* browsers.

- **Nav icons are served from R2** (`https://cdn.sgxp.me/img/nav_icons/`), and the Navbar preloads them all (`NAV_ICON_FILES`) because dropdown contents don't exist until opened - add any new icon to that list too.

- **Dialogs/sheets owned by the Navbar (or anything `transition:persist`ed) must not portal to `<body>`.** Astro's router swaps in a brand-new `<body>` element on every client-side navigation, and bits-ui's `Portal` resolves its target once, at mount - so after the first navigation the sheet "opens" (state flips, fetches fire) into the old, detached body and nothing appears. Only reproducible by arriving via the navbar, never on a fresh load. Render in place instead: `portalProps={{ disabled: true }}` on `Sheet.Content`, as the mobile menu does (the themed `Sheet` wrapper doesn't pass `portalProps` through - add it if needed), and raise its z-index since it's then stacked where the navbar sits in the page. (Hit by a navbar Bookmarks sheet on 2026-09-25, later replaced by the `/bookmarks` page.)

- **The dev server can keep serving a Svelte component's *old* `<style>` after edits** (seen 2026-09-26 during the button migration): the component's JS updated, but its `?svelte&type=style` module still had deleted rules, so the page looked half-migrated. Check with `curl -s "http://localhost:4321/src/components/X.svelte?svelte&type=style&lang.css"`; `touch` the file to make the watcher rebuild it (no restart needed), then hard refresh. Re-check before trusting a before/after screenshot.

- **Vite dev dependency cache can desync mid-session** (serving pre-bundled chunks from two optimizer runs -> two copies of Svelte -> `effect_orphan` / hydration errors in a *fresh* browser while an already-open one looks fine). Fix: stop the dev server, `npx astro dev --force`, hard refresh.

- **Headless-browser verification works well here** (puppeteer-core against the installed Chrome and Firefox): measuring glyph/pixel positions, comparing browsers, and checking CDP `LayerTree` compositing reasons. Headless Chrome doesn't finish the dropdown fade-in animation, so disable animations when screenshotting menus.

## Soda-Kan customization (added 2026-09-24)

- **The navbar presence cans are drawn from `src/lib/sodaCan.ts`, not PNGs.** The two frames (5x8 idle, 7x6 hop) are pixel grids of palette slots, rendered to memoized SVG data URLs by `canSpriteUrl(frame, choice)` (works in SSR and the browser). The classic palette is verified pixel-identical to the old `public/sprites/presence/*.png`, which are no longer referenced.
- **Users store preset ids, not colors**: `Users.sodaCan.body` / `.eyes` (a CMS `group` of two `text` fields; the CMS checks only the id *format*). Add new presets to `BODY_PRESETS`/`EYE_PRESETS` with a site deploy alone - unknown ids render as classic. Use hand-picked 3-step ramps for bodies; single-color-derived shading looks muddy at this size.
- Flow: `resolveUser`'s cached user carries `sodaCan` (bumped `CACHE_VERSION` to 2 for it) -> `presence/stream.ts` passes it to `joinPresence` -> snapshot entries carry `can`. Saving a profile calls `updatePresenceCan()` from `api/users/update.ts` (same process as the hub), so the can recolors live for everyone. Shown on profiles via `ProfileSodaCan.svelte`, edited via `SodaCanPicker.svelte` in `EditProfileModal`.
- The "you" marker on your own can is a 3x2 pixel arrow (`.presence-you-marker`); the bar is `2 * MARKER_SPACE` taller to fit it at the top of a leap, with the cans raised by `MARKER_SPACE` so they don't move on screen.
- **Shared stage (phase 1, 2026-09-24): the server owns the scene.** `src/lib/presenceStage.ts` (pure rules) + `presenceHub.ts` (state + a 250ms hop clock that only runs while someone's online) decide every can's position, layer and size; `PresenceCans.svelte` only renders it. Events: `presence-update` (full snapshot `{ total, hidden, entries }`, on join/leave/recolor) and `presence-hops` (batched `[{ id, x, dir }]`). Hops are committed server-side the instant they start, so later hops plan around landing spots.
  - Positions are "bar units" (0-330 = the narrowest bar, a 1280px screen); each browser maps them onto a play area capped at 640px and centered in the bar. Members never overlap on any screen; only gaps stretch, sprites are never scaled.
  - Crowding steps: everyone 2x side by side (<=20 cans) -> members 2x in front, visitors 1x in a dimmer overlapping background layer (<=20 members) -> members 1x (<=41) -> newest fold into "+N". Visitors past 40 also fold. Stepping back up needs 85% room (hysteresis), and the "+N" chip's 28 units come out of the budget - forgetting that let cans get pushed off-stage (caught by a randomized join/leave/hop stress test).
  - Folded entries still ship in the snapshot (with an x) so a viewer whose own can is folded still sees it, drawn as a background can with the arrow.
  - Phases 2 (steer your own can) and 3 (chat bubbles, members only, moderated) are planned on top of this; the planning mock-up is the "Soda-Kan Crowd Scenarios" artifact.

## Theme scenery (rebuilt 2026-09-24 for performance)

- **Theme backgrounds are no longer `body` background layers.** Each theme's scenery lives in `src/lib/themeBackdrops.ts` (layer list: image, tile size, anchor/offset, speed px/s, drift) and is rendered by `src/components/ThemeBackdrop.astro` (mounted once in `FrontPageLayout.astro`, `transition:persist`ed) as fixed elements animated with `transform`. `public/themes.css` now only holds each theme's colors + `body` background-color.
  - Why: the old `background-position` animations on `body` with `background-attachment: fixed` repainted the whole screen with every layer on the main thread every frame (60 style recalcs/s; 28-46% of a 6x-throttled main thread for DDZ/ARK/Snow/HPZ/SSZ) and again on every scroll. Now: ~1-2% idle, 0 recalcs/s, scrolling roughly halved. Measured with CDP `Performance.getMetrics` + `Emulation.setCPUThrottlingRate` in headless Chrome.
  - Each moving layer is one tile wider than the viewport and loops over exactly one tile width (seamless; the old 200s loop had a visible jump). `steps(<tile width>)` timing moves it whole pixels so pixel art isn't resampled on the compositor; CSS vars in keyframes/`steps()` still run on the compositor (verified: zero main-thread recalcs).
  - **Tile sizes in the config must match the real images** - the loop distance depends on them. Re-check with sharp if an image on R2 changes.
  - All 8 themes' backdrops are in the DOM; CSS shows only `:root[data-theme]`'s, so the navbar's theme switch needs no JS here and hidden themes' images never download.
  - Ark's Sonic-zoom easter egg (`sonicZoomIn`, `.zoom-to-sonic`, `public/js/arkanimation.js`) was already disabled (script commented out in the layout) and animated the old body backgrounds; it would need reworking against `.theme-backdrop[data-backdrop="ark"]` if revived.
- **Don't drive the scenery with long Web Animations keyframe lists.** A tried-and-reverted "shared 30fps clock" rebuilt every layer's loop as a WAAPI animation with one keyframe per pixel step (hundreds to thousands each). Chrome handled it, but Firefox fell to 6-15 fps on the whole page (Sky Sanctuary 6.6 fps - even the presence cans stuttered), and its GPU use only *looked* lower because it was drawing fewer frames. Plain CSS `steps()` animations (2 keyframes) keep Firefox at 60 fps. When measuring GPU cost, always check the real frame rate too (count rAFs in a visible window).
- **Animated GIFs in the scenery are pre-rendered** by `scripts/generate-backdrop-sprites.mjs` into `public/themes/prerendered/` + `src/lib/backdropSprites.ts`. Fly-bys (`flyby: true` layers - characters on 6000-12000px-wide GIF strips that made the browser redraw the whole strip on every GIF frame) became sprite sheets in a character-sized `.bd-flyby` box: CSS `steps()` over the same loop distance, starting just off the left edge with a negative `animation-delay` to keep the original phase, and a `.bd-frames` strip stepping through the frames at the GIF's own rate. Snow's twinkling pattern is frozen on frame 1 (the flakes still fall), and DDZ/ARK's two still star layers are merged into one image. Pixel-compared against the GIF version at the same loop time: identical apart from sprite poses.
- **"Motion: on/off"** (bottom of the desktop navbar theme menu) sets a `motion` cookie; FrontPageLayout renders `<html data-motion="off">` from it (no flash of motion), and ThemeBackdrop's CSS then holds every scenery layer still - 0% GPU in Firefox for every theme, same as MFZ. For slower computers, especially on Firefox.
- **Measuring scenery GPU cost:** headless Chrome under-reports it (no real window/present). Use a visible browser window and the Windows `\GPU Engine(*)\Utilization Percentage` counters for that browser's own processes (Firefox's GPU process is a child of the main one, so match by parent PID, not command line). On the dev machine (1080p60, integrated Radeon), `csrss.exe` alone showed ~25-33% 3D-engine use with no browser open, which Task Manager's overall GPU % includes. At 60 fps, Firefox / Chrome busiest engine, before -> after the pre-rendering: DDZ 21.5/6.4% -> 14.0/5.5%, HPZ 14.6/5.5% -> 7.8/3.4%, SSZ 16.0/8.6% -> 12.0/7.1%, Snow 19.4/13.8% -> 21.5/9.9% (Snow's cost in Firefox is its two full-screen falling layers, not the GIF). Firefox generally costs 2-3x Chrome for moving scenery.

## Idle-performance pass (2026-09-24)

- **Anything that asks for a main-thread frame every frame makes the whole page pay for it.** The backdrop's compositor animations cost ~nothing on their own, but while *any* rAF loop or main-thread-ticked animation is running, every frame also re-services all 19 backdrop animations and pre-paints/layerizes the whole DOM (~7k elements on /sprites). Measured at 6x CPU throttle: idle /sprites went from ~90% to ~30% main-thread busy after removing the three such sources below. Before adding any always-on animation, check it doesn't bring `RecalcStyleCount` back to ~60/s (`Performance.getMetrics` in headless Chrome, *without* a rAF-based fps counter in the harness - that counter itself forces frames).
  - **The /sprites logo is no longer three.js.** `Logo3D.svelte` (a WebGL rAF loop), `three` at runtime and `public/models/sprites-logo.json` are gone. `scripts/generate-sprites-logo.mjs` renders the same extruded text once (letters spaced 0.5 units, 2px white edges, 2px black + 2px white outer ring) into two alpha masks, `public/img/sprites-logo-{light,dark}-{1x,2x}.png`; `.sprites-logo` in `SpriteBrowser.svelte` paints them in `--font-color` and `color-mix(in srgb, var(--page-color) 60%, black)`. The masks are split so stacking dark-then-light composites exactly. `three`/`@types/three`/`puppeteer-core` are devDependencies only for that script.
  - **Animate `transform`, not the individual `translate` property** - Chrome ticked the "you" arrow's `translate` bob on the main thread every frame; the same keyframes as `transform` stay on the compositor.
  - The presence can flip is now instant (no `transition: transform` on `.presence-can-img`).
- **Sprite-card text is class-based glyph spans built as HTML strings** (`src/lib/spriteCardText.ts`, one implementation for SpriteBrowser, SpriteCard, ProfileSprites and ProfileFavorites). Each character is `<span class="sg sg-<codepoint>">` (`sn-` for altNumberMap); the sizes/atlas offsets are one stylesheet generated from charMap, served prerendered as `/sprite-glyphs.css?v=<content hash>` (`src/pages/sprite-glyphs.css.ts`, linked in FrontPageLayout). Components render the fields with `{@html}` - safe because only characters present in charMap ever emit markup. The text is now in the server-rendered HTML (it used to be filled in by a requestIdleCallback after hydration, as ~250-char inline styles per span); verified pixel-identical on /sprites and both profile grids. Upload dates render in UTC on the server and switch to the viewer's timezone on mount (`spriteCardText(sprite, { localDate: mounted })`).
- **The /sprites grid stays mounted while the in-page viewer is open** (`display: none` + a Web Animations slide instead of `{#if}` + Svelte `fly`), so closing a sprite doesn't rebuild the grid. On the Astro-intercepted back-navigation, `handleAstroBeforeSwap` sets `scroll-behavior: auto` on <html> until `showBrowserAgain` has restored scroll: the router's own (smooth) scroll restore was still animating when ours ran, and Chrome kept applying the rest of it, landing 100-250px too far down whenever /sprites had been reached through the navbar.
- **Never call `toLocaleDateString`/`toLocaleString` per item in a hot render path** - it builds a new `Intl.DateTimeFormat` every call. That alone was ~330ms of /sprites' ~560ms hydration at 6x throttling (73 cards, formatted twice). Build the formatter once and reuse it (`spriteCardText.ts` does). Also: the /sprites island's 217KB of serialized props costs only ~30ms to parse - not worth trimming.
- **SmackJeevesArchiveTable renders only the visible view** (`showTable` = 1400px+ media query AND the Table toggle); it used to render the full TanStack table hidden behind the default card view on every page. Its uploaded-comics list is cached for 5 minutes in a `<script module>` variable (Astro's router keeps modules loaded across navigations), so return visits skip the ~900-entry download; each fresh visit still reshuffles.
- **Known leaks:** each client-side visit to `/` still adds ~34 JS event listeners and ~180 nodes that are never released (~0.1MB); they're not in the live DOM, not in any extra Document, not window/document listeners, and not Svelte transition leftovers (checked) - heap-snapshot growth is Text/HTMLImageLoader/ElementAnimations, i.e. what looks like the old Posts.svelte subtree. Low impact, parked. The /sprites leak (was ~4.5MB/visit) dropped to ~0.5MB/visit after the card-text rewrite.
